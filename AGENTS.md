# Контекст семейства manipulation

## Область действия

Этот файл задаёт правила для всех семи пакетов семейства. В monorepo он
уточняет родительский `AGENTS.md`; в отдельном checkout действует самостоятельно.
Семейство показывает расширяемую объектную манипуляцию: общие
контракты и механизмы не зависят от робота, а Franka служит прикладным примером
их сборки в работающую систему.

Текущий уровень доверия семейства — `candidate`. Основной путь строится на
MoveIt. cuRobo остается необязательным экспериментальным PlannerManager backend
за тем же MoveIt-контрактом.
Точное текущее состояние и незакрытые критерии находятся в `ROADMAP.md`.

## Общие правила разработки

- Перед правками проверить Git status, прочитать затронутые README и ROADMAP.
  Сохранять чужие изменения; commit, push и публикация выполняются по запросу.
- Не менять публичные ROS-контракты скрытно. Правила совместимости находятся
  в `docs/CHANGE_CONTROL.md`, команды сборки и проверки — в `INSTALL.md`.
- Каждый исходный, интерфейсный и комментируемый конфигурационный файл начинает
  краткое описание `Responsibility`. Оно объясняет роль и инварианты файла.
- Изолируемую новую логику покрывать быстрыми тестами. Проверять фактическую
  регистрацию и выполнение тестов; сборка и unit-тесты не доказывают runtime.
- Не скачивать модели/SDK автоматически; не принимать чужие лицензии за
  пользователя. Завершать только процессы, запущенные своей проверкой.
- `candidate` означает незавершённую приёмку. `canonical` требует воспроизводимых
  проверок всех заявленных возможностей на чистом commit. Не повышать статус
  по одной успешной сборке.

## Реализованные границы

Эти границы уже являются частью рекомендуемой архитектуры и должны сохраняться:

- `manipulation_msgs` владеет общими ROS-сообщениями, сервисами и actions. В нем
  нет сценария Franka, восприятия, симулятора или реализации planner backend.
- `manipulation` владеет robot-independent состоянием задач, жизненным циклом,
  координацией PlanningScene и агрегированием здоровья системы.
- `manipulation_moveit` адаптирует общие контракты к MoveIt: planned transfer,
  MoveIt Servo, PlanningScene и occupancy map. Модели робота и сценарные
  значения ему не принадлежат.
- `manipulation_perception` приводит источники stereo, детекции и оценки позы к
  общим stamped ROS-интерфейсам. Зависимости NVIDIA изолированы в
  `manipulation_perception_isaac_ros`.
- `franka_motion` владеет конкретикой Panda: description, ros2_control,
  MoveIt-конфигурацией, мирами симуляторов, профилями и сценариями запуска.
- `manipulation_curobo` является необязательным `experimental-backend`. Он не
  определяет второй язык задач и не становится зависимостью основного пути.

Generic-пакеты не должны включать `franka_motion`, имена Panda, конкретный мир
или координаты демонстрационного сценария. Прикладной пакет может зависеть от
generic-пакетов и связывать их конфигурацией; обратная зависимость запрещена.

## Контракты данных и backend

- Потребители зависят от общих контрактов, а не от внутреннего класса MoveIt,
  cuRobo, detector или pose estimator.
- Заменяемые реализации сходятся к одному контракту. Новый backend добавляется
  адаптером и не протаскивает собственные типы через весь workflow.
- Связанные perception-данные передаются stamped-сообщениями и сопоставляются по
  `stamp` и `frame_id`. Нельзя восстанавливать синхронизацию по одному payload.
- На границах обязательно проверяются конечность чисел, ожидаемый frame,
  доступность TF для нужного времени и свежесть наблюдения. Предметные
  ограничения конкретной задачи оформляются отдельной policy, а не скрытой
  проверкой generic workflow.
- Публичные ROS-контракты меняются только явной миграцией. Временный bridge или
  alias должен быть помечен как compatibility и не выглядеть равноправным
  рекомендуемым API.

## PlanningScene и состояние мира

Рекомендуемый путь использует coordinator как единственного владельца записи в
PlanningScene. Операции над world и attached object выполняются через lease,
session и revision, чтобы независимые узлы не перезаписывали состояние друг
друга.

Backend может читать или зеркалировать авторитетную сцену через адаптер, но не
создает параллельного источника истины. Неопределенный результат записи должен
оставаться неопределенным до reconciliation; его нельзя молча считать успехом.

Поддерживаемый V2-путь не содержит прямого writer-а PlanningScene в task-клиенте,
стратегии или planner backend. Compatibility escape hatch не является частью
рекомендуемого графа и не должен возвращаться в новый код.

## Жизненный цикл задачи

- Долгая операция предоставляется action-сервером с feedback, cancel, pause и
  явным terminal result. Одноразовый клиент только формирует цель и отображает
  результат; после принятия goal он не вводит whole-result deadline.
- Оркестрация задачи, владение worker и recovery находятся в одном серверном
  пути. Launch и demo entrypoint не реализуют стадии движения самостоятельно.
- Чистые state machine и policy не должны владеть ROS-нодами, TF buffer, MoveIt
  объектами или процессами. ROS-коммуникация и side effects находятся в
  адаптерах.
- Отмена относится к конкретно принятой цели. После ошибки или cancel система
  сохраняет лучшее доказанное положение объекта и выполняет только обоснованный
  recovery.
- MoveIt является основным backend для planned-движения. MoveIt Servo —
  отдельный реактивный механизм и не подменяет обычное планирование. cuRobo
  оценивается через тот же внешний контракт, но остается экспериментальным.

## Общий V2 путь

В исходниках уже реализованы один `TransferObjectSequenceV2` server для
configured/detected intent, `ObjectCatalog` с primitive/mesh/compound geometry,
отдельные observation/grasp providers, `ResolvedTransferTask` и C++ registry
стратегий с единственной production-реализацией `pick_lift_place`. Старые
static/detected actions и нижний transfer action удалены.

Это не означает автоматического завершения задач roadmap: их статус определяется
только `ROADMAP.md` после предусмотренных package и runtime-проверок.

Текущие статусы, выполненные проверки и оставшиеся критерии читать в
соответствующих карточках `ROADMAP.md`. Не дублировать изменяемые списки задач
в этом файле и не выводить общий уровень доверия из статуса отдельной задачи.

## Операционные skills

- Для полной runtime-проверки Franka в Gazebo или Isaac Sim использовать
  `$validate-franka-manipulation`.
- Для отдельной диагностики stereo и perception pipeline использовать
  `$diagnose-franka-perception`.

Skills задают воспроизводимую процедуру, но не являются источником
архитектурной истины. Актуальные границы берутся из этого файла, состояние работ
из `ROADMAP.md`, а ROS-контракты из кода и API-документации пакетов.

## Порядок изменения

1. До архитектурной правки прочитать `README.md` и соответствующий пункт
   `ROADMAP.md`.
2. Определить, меняется ли общий контракт, generic-компонент, backend-адаптер или
   только Franka-сценарий.
3. Не переносить robot-specific детали в общий слой ради быстрого запуска.
4. Изолируемую логику проверить без симулятора; runtime-возможность проверить в
   заявленном Gazebo, Isaac или hardware-профиле.
5. При изменении зависимостей, границ модулей или пакетов, общего контракта либо
   самих архитектурных проверок выполнить `scripts/check_architecture.py`
   командой из README, даже если обычная проверка выбирает только один пакет.
   Это быстрые проверки исходников всего семейства; сборка, installed/wire
   contract tests и необходимая runtime-приёмка выполняются отдельно по задаче.
6. Обновить README и ROADMAP только после фактической реализации и проверки; не
   повышать статус по результатам одной сборки или unit-тестов.
